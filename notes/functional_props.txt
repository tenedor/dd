Proposal:
- Model objects and primitives (data) are passed as props to views. A view must
  rerender when any of its data changes in a way that influences its rendering.
- For a view to rerender, it must learn something changed. It either takes
  responsibility for finding out on its own (it listens for props' changes) or it
  is told. Likewise, it either receives distinguishably new props or its
  force-update method is called.
- Reject using force-update as a general pattern; reserve it for rare difficult
  cases. Force-update rejects the functional-reactive pattern.
- Thus model objects must in general receive distinguishably new props whenever
  they ought to update.
- Primitive props are different exactly if they are value-different.
- Model object props are different by being either pointer-different or
  contents-different. Contents-different matters but testing it literally is
  expensive in linear scale with with the size of the object being tested. In a
  a functional paradigm, values are never contents-different without being
  pointer-different, but this requires that for any change all parent objects of
  the changed value are replaced with a new copy. The parent objects can
  optionally replace unchanged children as well but this can unnecessarily cause
  pointer-different values at the scale of the object's size.
- In a functional model, either changes can only be made top down or changes must
  be propagating up to parents. Requiring top-down changes breaks the modularity
  of local reasoning so fuck that - require that changes propagate up to parents.
- Every model object has one or more parents. (The top-level node has a parent
  that is not a model object.) objects change through create, modify, and delete.
  - For create, the object must be introduced to its parent, satisfying the
    notification constraint.
  - For modify, the object must tell each parent. Objects do not generally know
    their parents so they must have a callback to tell each parent.
    - If objects only ever have one parent, this can be passed at construction.
      else there must be a way to register listeners
  - For delete, the object must either only be deleted by removal from all
    parents or it must notify its parents to remove it.
- In a functional design, objects are not value-different without being
  pointer-different. This requires an object to replace a changed child object
  with a copy, and the act of replacing it requires identifying the child's
  location, which may be in a list that wouldn't otherwise be indexed usefully,
  and in general is a pain in the ass.
- A functional-identifier design relaxes the functional design by maintaining an
  identifier on each model object. The identifier is not part of the object's
  logical value. If the same object at two observations is value-different then
  its identifier must be different. A view does not need to rerender if the
  identifiers of its data dependencies have not changed since its previous render.
  However, the view now needs another way to be told that values might have
  changed. Since we restrict ourselves to props for this communication, an
  additional prop must be passed that changes whenever at least one of the view's
  data dependencies has changed. (It might change more often.)
- In general a view needs to remember the identifier-set it used on its last
  render to take advantage of this. However, a functional-timestamp design
  requires just one integer to be stored by using epoch numbers (timestamps) as
  identifiers. Epoch numbers increase on every operation, so if the highest epoch
  number of a view's data dependencies is no higher than at its last rendering it
  need not rerender. The view can avoid storing a new integer for this if the prop
  it receives notifying it to check for changed dependencies is the current epoch
  number - the view already has access to its previous props at comparison-time.
- A functional-timestamp design (plus the assumptions above) requires that every
  op reads and increments a global epoch number, records this number on the
  changed model object, and propagates this value to its ancestors. It requires
  that a view test its props' epoch numbers whenever its props change to determine
  if it needs to rerender.
- In javascript, model objects may be non-primitive literals (objects or arrays)
  or instances of custom model classes. Custom classes will all inherit from the
  base model class and have the required properties. Non-primitive (np) literals
  are trickier. Reject monkeypatching Object.prototype because typescript won't
  play well with this (well, maybe there's a hack for it) and it's a gross hack.
  Thus, any np-literal passed as a prop must either self-signal every time it
  changes (ie be pointer-different or be accompanied by an additional indicator of
  changes) or the receiving class must rerender whenever it hasn't verified that
  all members of the literal are unchanged. Reject the latter option as it
  forfeits cheapness by forfeiting functional equality testing.
- Thus, either:
  1. Don't pass non-primitive literals as props; always wrap them in a class.
      1a. Don't pass logical np-literals ever.
      1b. Only pass logical np-literals with a wrapper class around them.
  2. Only violate the above when the np-literals never change.
  3. Only violate the above when any content-different np-literal is always
      pointer-different.
  4. Only violate the above when any np-literal is accompanied by an external
      marker of changes (e.g. an epoch number).
- Considerations:
  1a. Object literals are lightweight data structures that concisely express
      storage that is uncoupled from procedures. Classes are a bulkier superset
      of object literals that only add value when coupling procedures to data or
      customizing access patterns - which is often not needed. Meanwhile array
      literals are not supersetted by classes and can only be replaced by classes
      by being wrapped. Avoiding logical np-literals creates lots of avoidable
      boilerplate.
      -> REJECT.
  1b. The wrapper class either proxies the underlying np-literal's interface (1)
      or provides access to the underlying np-literal (2-4). In the non-proxy case,

      two characters (e.g. `.o` and `.a`), but writes need to update the epoch

        automated proxying there'd need to be a custom wrapper object for every
        object type, and array indexing syntax would be lost for working with
        arrays. Gross.
        -> REJECT.

      3. Offer write-permissioned access to the underlying np-literal and

- Sketch of functional-timestamp classes:

  class EpochManager {
    private epoch: number = 0;

    public get epoch(): number {
      return this.epoch;
    }

    public nextEpoch(): number {
      this.epoch++;
      return this.epoch;
    };
  }

  type EpochUpdateListener = (epoch: number) => void;

  class BaseModel {
    public epoch: number;
    protected readonly epochManager: EpochManager;
    private epochUpdateListeners: EpochUpdateListener[] = [];

    constructor(epochManager: EpochManager) {
      this.epochManager = epochManager;
      this.epoch = epochManager.epoch;
    }

    public listenForEpochUpdate(onEpochUpdate: EpochUpdateListener) {
      this.epochUpdateListeners.push(onEpochUpdate);
    }

    protected onDependencyEpochUpdated(epoch: number) {
      if (this.epoch < epoch) {
        this.epoch = epoch;
        this.epochUpdateListeners.forEach(listener => listener(this.epoch));
      }
    }

    protected onSelfMutated() {
      this.epoch = this.epochManager.nextEpoch();
      this.epochUpdateListeners.forEach(listener => listener(this.epoch));
    }
  }

  class SomeModel extends BaseModel {
    private prim: number;
    private obj: OtherModel;

    constructor(epochManager: EpochManager, prim: number) {
      super(epochManager);

      this.prim = prim;
      this.obj = new OtherModel(this.epochManager);
      this.obj.listenForEpochUpdate(this.onDependencyEpochUpdated);
    }

    public get prim(): number {
      return this.prim;
    }

    public set prim(prim: number) {
      this.prim = prim;
      this.onSelfMutated();
    }

    public get obj(): OtherModel {
      return this.obj;
    }

    public set obj(obj: OtherModel) {
      this.obj = obj;
      this.onSelfMutated();
    }
  }

  class BaseComponent<P, S> extends React.Component<P, S> {
    private lastRenderedEpoch: number = -1;

    // TODO - move this to a helper that takes a list of props to ignore so that
    // derived classes can reuse the part of the logic that they want
    public shouldComponentUpdate(props: Props) {
      if (!Object.keys(props).equals(Object.keys(this.props))) {
        return true;
      }
      for ((k, v) in props) {
        if (k === "epoch") {
          continue;
        }
        if (v !== this.props[k] ||
            (!isPrimitive(v) && v.epoch > this.lastRenderedEpoch)) {
          return true;
        }
      }
      return false;
    }

    public componentDidUpdate() {
      this.lastRenderedEpoch = this.props.epoch;
    }
  }

  export class BaseComponent<P extends BaseProps, S> extends React.Component<P, S> {
    private lastRenderedEpoch: number = -1;

    public shouldComponentUpdate(nextProps: Readonly<P>): boolean {
      // keysEqual returns false if the two props objects have different keys
      if (!keysEqual(this.props, nextProps)) {
        return true;
      }
      for (const k in nextProps) {
        if (k === "epoch") {
          continue;
        }
        const v = nextProps[k];
        if (v !== this.props[k] ||
            (v instanceof BaseModel && v.epoch > this.lastRenderedEpoch)) {
          return true;
        }
      }
      return false;
    }

    public componentDidUpdate() {
      this.lastRenderedEpoch = this.props.epoch;
    }
